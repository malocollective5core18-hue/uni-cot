# Production bottleneck and failure-mode review

Reviewed: 2026-09-19. This is a static code review of the Django application, templates, migrations, and repository deployment assets. It does not include production metrics, PostgreSQL query plans, or a load test.

## Executive summary

The project has several real scaling safeguards (tenant/owner scoping, pagination, indexes in `core` migration `0004`, cache-key tenant scoping, and some row locking). The main production risk is not a single slow query; it is the combined request rate generated by browser polling, forced session persistence, and extra tenant lookups. At the same time, tenant signup and founder reporting perform work proportional to the number of migrations or tenants within ordinary web requests.

Address the first five items before a public launch or meaningful growth. They can cause timeouts, database saturation, inconsistent results across workers, or requests that grow linearly with tenant count.

## Findings

| Priority | Bottleneck / failure mode | Evidence | Production impact | Recommended correction |
| --- | --- | --- | --- | --- |
| P0 | **Every request writes the session.** | `mysite/mysite/settings.py:414` sets `SESSION_SAVE_EVERY_REQUEST = True`; the default Django session engine is therefore the database-backed default unless deployment overrides it. | Read-heavy pages and polling endpoints create a database write, cookie refresh, and session-row contention per request. At 100 active users polling once per 10 seconds, this setting alone can mean roughly 10 writes/second before normal application writes. | Set it to `False`. Use a shared Redis session backend for production, set an intentional expiry on login, and measure session-table write rate. |
| P0 | **Client polling produces a continuous database/API load and bypasses the short API cache.** | `templates/properties.html:2680` polls properties every 3 seconds; `templates/system_index.html:12922` polls cards every 10 seconds; groups polls every 15 seconds (`templates/groups.html:2903`). The system template has 75 `fetch()` calls and 9 intervals (410 KB); its calls use `{ cache: 'no-store' }` at e.g. `:12891`. | Each open tab repeatedly requests, deserializes, and compares entire datasets. The 3-second property poll is 1,200 requests/hour/tab; with forced session saving, it also becomes 1,200 session writes/hour/tab. Multiple tabs multiply the load. | Replace polling with SSE/WebSockets or version/ETag endpoints plus exponential backoff. Poll only the visible component, use a much longer interval as fallback, and return a changed/not-changed version before downloading rows. Do not use `no-store` for data that has server-side cache semantics. |
| P0 | **Tenant schema creation/migrations run synchronously inside owner-signup transactions.** | `service/views.py:1525-1535` wraps owner creation and `create_owner_tenant()` in `transaction.atomic()`. `customers/models.py:351-356` defaults `TENANT_PROVISION_SYNC` to `true`; `ensure_tenant_schema_ready()` may create a schema or invoke `migrate_schemas` (`:37-60`). | A signup holds an HTTP worker and transaction while DDL/migrations run. It is slow, can exceed proxy timeouts, locks resources, and concurrent signups can contend. A failed/restarted request creates difficult partial-provisioning states. Setting the flag false merely logs a deferred job; it does not enqueue one (`:355-356`), so the tenant may never be provisioned. | Commit a small tenant record with a `provisioning` state, enqueue an idempotent background job, and only expose the tenant once a health check confirms its schema/migrations. Use retries, a unique/idempotency key, and alert on stuck provisioning. |
| P0 | **Founder dashboard has N+1 queries and an N-schema fan-out.** | The loop at `core/views.py:756-769` runs once per tenant. For each tenant it calls `_get_tenant_owner()` (`:757`, a public-schema query) and `_get_tenant_data_summary()` (`:759`), which switches schema and runs up to four aggregates/counts at `:223-235`; it also issues extra subscription/domain/count queries in the loop. | Page latency and database connections grow roughly with tenant count. With dozens/hundreds of tenants, one founder page can execute hundreds/thousands of queries and schema switches, potentially exhausting the web worker or DB pool. | Store denormalized per-tenant dashboard counters, update them transactionally/on a queue, and show a paginated tenant list. Fetch public tenant metadata in bounded bulk queries; load detailed per-tenant metrics only on demand or asynchronously. |
| P0 | **Public/member login scans every active tenant and database schema.** | When no tenant is in the request, `_find_member_login_record()` loads all active tenants (`service/views.py:366-367`) then loops over them and switches schema (`:369-395`), checking a password in each (`:387-388`). | Login time is O(number of active tenants), with one or more database trips/schema switches per tenant. It will cause slow logins and can be abused to spend CPU on password hashes and database work. | Require/select a tenant before member authentication, or maintain a public indexed identity registry mapping an immutable login identifier to exactly one tenant. Add an IP/account rate limiter in shared Redis and a hard upper bound on expensive authentication work per request. |
| P1 | **Local-memory cache is the production fallback, so cache and invalidation are per worker.** | Settings select `LocMemCache` when `REDIS_URL` is absent (`mysite/mysite/settings.py:320-344`); API payloads are cached/invalidation is version-based in `core/views.py:123-157`. | With multiple Gunicorn workers/instances, each has a different cache. One worker may serve stale data after another handles a write; cache hit rate is reduced and cold-cache traffic can stampede the DB. `IGNORE_EXCEPTIONS=True` also silently turns Redis outages into cache misses. | Make Redis mandatory for production, use a distinct namespace/key prefix, expose cache health/metrics, and choose an explicit degradation policy. Add short lock/stale-while-revalidate protection for expensive builders. |
| P1 | **List endpoints permit 1,000 records and some endpoints materialize all records anyway.** | `_paginate_queryset()` allows `page_size` up to 1000 (`core/views.py:482-499`). The UI requests `page_size=1000` for users/tables/groups (e.g. `templates/system_index.html:7833`, `:8222`, `:8982`). `api_external_tables(...include_records=1)` iterates every matching record before retaining at most the per-table limit (`core/views.py:2342-2425`); `api_groups` serializes every membership for the selected groups (`:1510-1556`). | Memory, JSON payload size, DB work, and browser rendering grow with tenant data. The external-table implementation can scan far more than the response asks for. A few large tenants can cause worker memory pressure/timeouts. | Reduce maximum page size (e.g. 100), require cursor pagination, forbid `include_records` on a list endpoint, and make records a separately paginated endpoint. Use SQL/window-function limits per table or issue bounded per-table queries; add response-size limits. |
| P1 | **`record_count` is recalculated with `COUNT(*)` after every record mutation.** | `_sync_external_table_record_count()` runs `ExternalTableRecord.objects.filter(table=table).count()` then saves the table (`core/views.py:465-467`); it is called after record create/update/delete at `:2528-2530`, `:2577-2580`, `:2592-2595`, and signup at `:2689-2692`. | Every mutation becomes at least an additional aggregate scan and write. Under concurrent writes, a computed count may be stale and repeatedly counting a large table becomes expensive. | Update with `F('record_count') + 1/-1` in a transaction for creations/deletions; do not change count on updates. Periodically reconcile asynchronously. |
| P1 | **Tenant resolution happens on every request and two tenant middlewares are active.** | `TenantMainMiddleware` is prepended at `mysite/mysite/settings.py:241-245`; the custom `TenantMiddleware` is also active at `:233`. The custom middleware queries `CRTenant` for each path URL (`tenant_middleware.py:84-106`) and performs one/two lookup attempts for subdomains (`:136-145`), then switches and resets schema for every response (`:71-76`). | Extra DB queries/schema switching sit in front of every request, including static-like app requests and polling. Two independent resolvers increase overhead and the chance that host- and path-based routing choose different contexts. | Pick one authoritative tenant-routing design. For path routing, replace/disable the incompatible resolver after integration testing; cache validated path-key-to-tenant mappings in Redis with safe invalidation. Ensure unknown tenant paths return 404 rather than executing in public schema. |
| P1 | **Tenant-key uniqueness is generated by loading all existing keys, with a race.** | `_generate_unique_tenant_key()` creates `set(CRTenant.objects.values_list(...))` at `customers/models.py:83-92`; it is used during tenant creation (`:318`). | Tenant creation gets slower as tenants grow. Two concurrent requests can select the same key before insert; the unique constraint then raises and makes signup fail instead of retrying. | Generate a fixed-length cryptographic key without a full-table read. Catch unique-constraint `IntegrityError` and retry a bounded number of times, or use a database-generated unique identifier. |
| P1 | **The UI is a set of very large, inline-script templates.** | `templates/system_index.html` is 410 KB / 13,949 lines, `external_tables.html` 213 KB, and `properties.html` 158 KB. The system template alone contains 75 fetch call sites. | Large uncached HTML increases TTFB/download/parse time, makes releases brittle, and makes it easy for duplicate timers/API flows to survive. Inline JS prevents normal immutable JS caching and makes CSP adoption difficult. | Split views into small templates and hashed static JS/CSS bundles; code-split administrative features, defer noncritical scripts, and set cache headers for versioned assets. Add template/bundle size budgets in CI. |
| P1 | **Cross-worker/session/deployment behavior is not specified in-repository.** | There is no `Procfile`, Dockerfile, `render.yaml`, Gunicorn config, health endpoint, CI workflow, or environment example in the repository root. Production settings require `DJANGO_SECRET_KEY`, PostgreSQL configuration, and—when `DEBUG=False`—a non-empty `DJANGO_ALLOWED_HOSTS` (`mysite/mysite/settings.py:51-103`). | A missing host value causes `DisallowedHost` for every production request; a wrong start command, worker count, migration sequence, or `collectstatic` step cannot be reproduced/reviewed from source. The checked-in `mysite/db.sqlite3` also risks confusing local/production data paths even though settings demand PostgreSQL. | Add a documented deployment contract: `.env.example` (no secrets), release command (`migrate_schemas`/bootstrap), Gunicorn command/timeouts/workers, `collectstatic`, health/readiness endpoints, and CI that runs checks/tests/migrations. Do not deploy the SQLite file. |
| P2 | **Error paths expose internal exception strings to clients.** | Many API handlers return `{'error': str(e)}` (e.g. `core/views.py:1160-1162`, `:2636-2638`, `:2698-2700`). | Database/schema/provider details are disclosed and callers receive inconsistent status handling; it also makes production error responses unreliable. | Log a structured exception with a request ID, return a generic stable error body, and use 4xx only for expected validation errors. |
| P2 | **Rate limits are session-local and client-resettable.** | `_rate_limit()` stores timestamp arrays in `request.session` in both apps (`core/views.py:69-82`, `service/views.py:185-200`). | An attacker can reset cookies/new sessions; limits are not shared across workers and, because sessions are saved, the limiter increases DB writes. It does not meaningfully protect login/signup endpoints. | Enforce Redis-backed limits keyed by IP + normalized account/tenant at the proxy/application boundary. Keep the session only for UI state, not abuse control. |

## Correctness and availability risks to fix alongside performance

- `api_external_table_signup()` does an `exists()` check and then inserts without a transaction or database uniqueness constraint (`core/views.py:2674-2691`). Concurrent submissions can create duplicates. Move identifying fields out of JSON into columns and add `UniqueConstraint(table, registration_number)`; catch the constraint error.
- Core ownership/group relations use untyped integer IDs rather than foreign keys (`core/models.py`, for example `UserGroupMember.user_id`/`group_id`). The code must emulate joins/scoping in many places, leaving orphan/consistency risks and preventing normal referential indexes/cascades. Migrate these to tenant-local foreign keys deliberately.
- A property claim is allowed without owner authentication when the request body resembles a claim (`core/views.py:1177-1211`). If that is intentional, constrain exactly which fields an anonymous claimant may change and use an unguessable claim token; otherwise require authentication. This is an abuse/availability risk as well as a data-integrity risk.

## Recommended execution order

1. Stop forced session saves; make Redis a required, monitored cache/session service.
2. Remove high-frequency full-list polling and cap/cursor-paginate all collections.
3. Move tenant provisioning into an idempotent worker and give tenants a provisioning lifecycle.
4. Redesign member identity lookup to avoid cross-schema login scans.
5. Replace founder per-tenant live aggregation with stored metrics and pagination.
6. Consolidate tenant middleware, then run load tests with realistic tenants, rows, browser tabs, and Gunicorn workers.
7. Add deployment/observability basics: structured logs, request latency/error rate, DB connection/pool metrics, cache hit rate, slow-query logging, uptime/readiness checks, and alerts.
