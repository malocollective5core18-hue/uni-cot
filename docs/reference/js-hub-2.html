js

js

Template literals

Backticks let you embed variables directly in a string — no more string concatenation with +.

js

Type coercion surprises

== converts types before comparing; === does not. This single difference prevents a huge class of bugs.

js

Numbers: NaN and Infinity

JavaScript has exactly one number type — but it has some famous edge-case values worth knowing by sight.

js

Truthy and falsy values

Every value is either truthy or falsy when used in a condition — only eight values are actually falsy.

Arithmetic operators

The usual six, plus ** for exponents — no separate power() function needed.

js

Comparison operators

Prefer === and !== almost always — they're predictable in a way == and != aren't.

js

Logical operators & short-circuiting

&& stops at the first falsy value; || stops at the first truthy one — used constantly for defaults.

The ternary operator

A one-line if/else that returns a value — perfect for a quick either/or decision.

js

?? only falls back on null/undefined — || falls back on ANY falsy value, including 0 and "", which is often wrong.

Control flow

How a program decides what to do next, and how to repeat an action without copy-pasting it.

if / else if / else

Checked top to bottom — the first true condition wins, the rest are skipped.

js

switch

Cleaner than a long if/else chain when you're comparing one value against many exact options.

js

for loop

The classic three-part loop — init, condition, and what runs after each pass.

js

while / do...while

while checks first, do...while runs once before checking — a subtle but real difference.

js

for...of vs. for...in

for...of iterates VALUES (arrays, strings); for...in iterates KEYS (object properties). Mixing them up is a classic bug.

js

break and continue

break exits the loop entirely. continue skips just this iteration and moves to the next.

Functions

Packaging logic so you write it once and reuse it — the single most important habit for clean code.

Declaration vs. expression

A function declaration is hoisted (usable before its definition); a function expression is not.

js

Arrow functions

Shorter syntax, and — importantly — no own `this`, which fixes a common bug from regular functions in callbacks.

js

Default parameters

A fallback value used only when the argument is omitted or undefined — no manual `if` needed inside the function.

Collects any number of extra arguments into a real array — no more juggling the old `arguments` object.

js

Closures

An inner function remembers the variables from where it was created, even after the outer function has finished running.

js

IIFE — Immediately Invoked Function Expression

Arrays

Creating & accessing arrays

Zero-indexed — the first item is index 0, and .length always tells you how many there are.

js

push / pop / shift / unshift

Add or remove from either end — push/pop work at the end, shift/unshift work at the start.

js

4Techniques that separate pros from beginners

💡 A "stack trace" is the red error text the browser prints in the Console tab (see DevTools above) — it's not something you generate, it just appears whenever code throws an error. debugger; is a real line of JavaScript you type directly into your own code file, wherever you want execution to pause.

Reading a stack trace

Read top to bottom: the top line is where it actually broke; each line below is who called who to get there. The FIRST line of your own code (not a library's) is almost always where the real fix belongs.

Breakpoints vs. debugger vs. logging

A breakpoint set in DevTools needs no code change. debugger; is the same thing, written INTO the source, so it travels with the file. console.log is fastest for a quick check, but leaves cleanup behind — breakpoints don't.

Debugging async code

Set "Async" call stacks stay on in DevTools (default) so a breakpoint inside a .then() or after an await still shows you the ORIGINAL caller — otherwise the trace just shows "Promise" and nothing useful.

Common error patterns

Cannot read properties of undefined → something you expected to exist doesn't yet (often a race with async data). is not a function → check the actual type at that line, not what you assumed it was. Maximum call stack → a recursive function with no base case.

Source maps

When code is minified or transpiled, a source map lets DevTools show you the ORIGINAL source instead of the compiled mess — so breakpoints and stack traces still point at lines you actually wrote.

Defensive habits

Validate function inputs early and throw with a clear message (Part 11). Prefer const so a value can't silently change underneath you. Never swallow an error in an empty catch {} — log or rethrow it.

6Pro debugging workflow checklist

A short process worth internalizing for life — run through it in order before you start guessing.

💡 This is a mental checklist, not a file or a tool — nothing to create or open. Next time something breaks, come back and walk down this list in order.
  1. Read the actual error message and the FIRST line of the stack trace that points to your own code — don't skim past it.
  2. Reproduce it reliably. If you can't make it happen on demand, you can't confirm it's fixed either.
  3. Form one specific hypothesis about the cause — not "something's wrong," but "I think X is undefined at this point."
  4. Set a breakpoint (or a debugger; statement) at the earliest point your hypothesis can be checked.
  5. Inspect the actual values in scope — don't assume, look.
  6. Fix the smallest thing that addresses the real cause, not just the symptom.
  7. Re-run the exact steps that reproduced it, to confirm it's actually gone.
  8. Ask whether the same mistake could exist anywhere else in the codebase, and check there too.
